# 公開用エミュレーターまでのおこなうことリスト

現行の残タスクは `docs/plan/active-implementation-plan.md` を正とする。
完了済みの仕様穴埋めと確率調整は `docs/plan/archive/completed-spec-and-simulation-tasks-2026-05-03.md` に移した。

## 目的

この資料は、`Nikechan Slot` をブラウザ上で公開できるスマートスロットエミュレーターにするまでの作業を、優先度順に整理する。

今日の制作作業、筐体の本制作、基板回路、実機製造、型式試験申請に必要な詳細資料は、この資料の直接対象外とする。ただし、将来実機化や検定資料化へ進む可能性を潰さないため、抽選、停止制御、入賞判定、払出などの遊技結果を決める処理と、液晶、音、ランプ、アニメーションなどの演出処理は初期段階から分離する。

## 公開可能の定義

公開可能な状態とは、以下を満たす状態を指す。

- ブラウザで起動できる
- 第一段階では、ターミナル風ログ画面で1ゲームずつメイン基板相当のログを確認できる
- 第一段階では、Bonusまで自動実行し、到達ゲームと内部状態をログで確認できる
- 手動で遊技できる
- 仕様書に基づいたリール、役、抽選、停止、入賞、払出が動作する
- 告知ランプまたは告知エリアと、液晶の `BONUS` 表示が動作する
- オートプレイで一定回数の試行を再現できる
- 出現率、払出、状態遷移の検証結果を確認できる
- 既存メーカー、既存機種、既存図柄、既存音源、既存告知ランプ意匠を使用していない
- エミュレーターであること、実機検定を通したものではないこと、実機化には別作業が必要なことが明記されている

## P0: 実装前に固定する仕様

公開用エミュレーターの土台になるため、最初に決める。

1. リール仕様を固定する
   - 3リール
   - 1リールあたりのコマ数
   - 図柄ID
   - 左、中、右リールの配列
   - 表示窓に見えるコマ数

2. 有効ラインと入賞判定を固定する
   - 有効ライン数
   - ライン定義
   - 入賞判定のタイミング
   - ボーナス成立後の持越し仕様
   - ボーナス成立とボーナス図柄入賞の違い
   - ボーナス図柄入賞後のボーナス状態開始条件

3. 役構成と払出を固定する
   - リプレイ
   - 小役
   - 通常小役
   - レア小役
   - レア小役の目押し要否
   - レア小役取りこぼし時の扱い
   - BIG
   - REG
   - ハズレ
   - 役ごとの払出枚数またはクレジット加算

4. 抽選仕様を固定する
   - 設定1から設定6
   - 現在設定の保持方法
   - 通常時の抽選テーブル
   - ボーナス成立状態の扱い
   - 設定別 BIG/REG の確率
   - 設定別 BELL/REPLAY の確率
   - CHERRY/SUIKA/ボーナス重複チェリーを全設定共通にする方針
   - 設定別 出玉率
   - ボーナスと小役の同時成立
   - 小役同士の同時成立禁止
   - 乱数シードの扱い

5. 停止制御の初期方針を固定する
   - 目押しをどこまで再現するか
   - 最大滑りコマ数
   - 成立役を引き込む優先順位
   - 通常小役を目押しなしで揃える制御
   - レア小役を目押し範囲内でのみ揃える制御
   - レア小役取りこぼし停止形
   - 未成立役を揃えない制御
   - ボーナス成立状態での目押し失敗時のリーチ目
   - ハズレ時の停止結果

6. ボーナス状態遷移を固定する
   - 通常時
   - ボーナス成立状態
   - ボーナス図柄入賞
   - ボーナス状態
   - 規定枚数到達後終了演出
   - 通常復帰

7. 告知仕様を固定する
   - 先告知または後告知
   - 告知ランプ点灯条件
   - 液晶 `BONUS` 表示条件
   - 告知と内部成立状態の関係

8. クレジットと操作仕様を固定する
   - MAX BET
   - START
   - 左、中、右 STOP
   - CREDIT 表示
   - PAYOUT 表示
   - 遊技開始に必要なクレジット

9. データ表示端末の仕様を固定する
   - 遊技機能から出力するイベント
   - 現在状態のスナップショット
   - 現在設定の表示
   - 動作回転数の定義
   - ボーナス間ゲーム数の定義
   - BIG/REG回数のカウントタイミング
   - 大当たり確率と小役成立確率の計算式
   - スランプグラフの差分計算

10. 第一段階ログシミュレーターの仕様を固定する
   - メイン基板相当ログの出力形式
   - 1ゲーム実行
   - Bonusまで実行
   - 停止条件
   - ログ表示行と構造化イベントの対応
   - 同じシードで同じログを再現する条件

## P1: コアエンジンを作る

UIより先に、遊技結果を決める処理を独立して作る。

1. データ定義を作る
   - `symbols.json`
   - `reels.json`
   - `roles.json`
   - `lines.json`
   - `stop-control.json`
   - `reach-patterns.json`
   - `bonus-spec.json`
   - `tables.json`
   - `settings.json`

2. コアモジュールを作る
   - 乱数
   - 現在設定
   - 設定別抽選テーブル解決
   - 役抽選
   - リール位置管理
   - 停止制御
   - 入賞判定
   - 払出
   - 状態遷移
   - クレジット管理
   - ボーナス状態管理
   - イベント出力

3. 演出と分離するためのイベントを定義する
   - `gameStarted`
   - `lotteryResolved`
   - `reelStopped`
   - `winEvaluated`
   - `payoutApplied`
   - `bonusFlagRaised`
   - `bonusSymbolEntered`
   - `bonusStarted`
   - `bonusEnded`
   - `bonusAnnounced`
   - `stateChanged`
   - `creditChanged`
   - `settingChanged`

4. 展示・デバッグ用アダプタの境界を作る
   - 通常抽選と強制成立を切り替える `OutcomeResolver`
   - 強制BIG/REG予約を保持する `ForcedOutcomeQueue`
   - BETからSTOPまでを自動実行する `AutoPlayer`
   - 通常WaitとWaitなしを切り替える `TimingProfile`
   - メイン基板相当ログへ変換する `MainBoardLogAdapter`
   - 通常操作、自動操作、強制成立を区別するログ

5. コアテストを作る
   - 同じシードで同じ結果になる
   - 成立役と停止結果が矛盾しない
   - 入賞ライン判定が仕様通りになる
   - 払出とクレジットが仕様通り増減する
   - ボーナス成立後の持越しが仕様通りになる
   - 強制成立を使わない通常抽選が独立して検証できる
   - 現在設定に対応した抽選テーブルが使われる
   - 設定別にBIG/REG確率が変わる
   - 設定別にBELL/REPLAY確率が変わる
   - CHERRY/SUIKA/ボーナス重複チェリーは全設定共通になる
   - ボーナス成立だけではボーナス状態へ移行しない
   - 未成立小役が有効ラインに揃わない
   - 通常小役成立時は目押ししなくても揃う
   - レア小役成立時は目押し範囲内でのみ揃う
   - レア小役取りこぼし時に未成立役が揃わない
   - ボーナス成立状態で目押し失敗時にボーナス図柄が揃わない
   - 1ゲーム実行でBETから状態遷移までログが出る
   - Bonusまで実行でボーナス内部成立までログが出続ける

## 初期アーキテクチャ方針

抽選と演出が密結合しないよう、最初から以下の境界を置く。

```text

  symbols.json
  reels.json
  roles.json
  lines.json
  stop-control.json
  reach-patterns.json
  bonus-spec.json
  tables.json
  settings.json

src/core/
  rng.ts
  setting.ts
  lottery-table.ts
  lottery.ts
  role-result.ts
  reel.ts
  stop-control.ts
  line-evaluator.ts
  bonus-state.ts
  payout.ts
  game-state.ts
  event-emitter.ts

src/emulator/
  game-service.ts
  outcome-resolver.ts
  auto-player.ts
  demo-controls.ts
  timing-profile.ts
  main-board-log-adapter.ts
  event-log.ts

src/simulator/

  run-until-bonus.ts
  batch-runner.ts

  terminal-log-view.ts
  canvas-renderer.ts

  sound.ts
  panels.ts
  assets.ts

src/terminal/
  data-counter.ts
  probability.ts
  slump-graph.ts
  terminal-panel.ts
```

守るべきルール:

- `core` は Canvas、音、DOM、画像ファイルに依存しない
- `ui` は抽選結果を決めない
- 強制BIG/REGは抽選テーブルを書き換えず、`OutcomeResolver` で次ゲームだけ差し込む
- オートモードは手動操作と同じコマンドを `game-service` に送る
- リールWaitなしは遊技結果ではなく `TimingProfile` の表示・操作タイミング設定として扱う
- `simulator` と `ui` は同じ `core` を使う
- 役抽選、停止制御、入賞判定、払出はログで再現できる
- 第一段階はCanvasなしで、メイン基板相当ログのターミナル風画面を先に作る
- 設定1から設定6を持ち、BIG/REG/BELL/REPLAY確率は設定別抽選テーブルで差をつける
- CHERRY/SUIKA/ボーナス重複チェリーは全設定共通にする
- ボーナス成立、ボーナス図柄入賞、ボーナス状態、終了演出、通常復帰を状態として分ける
- 停止制御は未成立役を揃えないことを最優先にする
- データ表示端末はイベントとスナップショットを購読するだけで、遊技状態を変更しない
- 演出は `core` から発火されるイベントを受けて表示する
- デバッグ表示は公開UIと分ける
- 最終的には、内部状態、Canvas筐体表示、筐体動作、シミュレーション操作、スランプグラフ、メイン基板ログを1つのブラウザUIに統合する
- 将来の主制御、副制御分離を意識し、遊技結果を決める処理と演出処理の境界を保つ
