# 予備適合性レビュー

取得日: 2026-05-01

## 結論

現時点のリポジトリ成果物だけでは、検定に通るかどうかは判定できない。判定は「未達」または「判定不可」とする。

理由:

- 実機が存在しない
- 主制御基板、副制御基板、ROM、回路図、構造図、動作原理図がない
- 遊技仕様、抽選テーブル、停止制御、払出、ボーナス仕様が未確定
- 出玉率、役物比率、短中長期試験、シミュレーション試験の結果がない
- 仕様書と実機の対比照合ができない
- スマートスロットとしての遊技メダル数表示、外部ユニット連携、送信操作仕様が未確定

したがって、現在の資料は「検定通過を保証する資料」ではなく、「検定通過に必要な設計・検証・証跡を作るための計画資料」である。

## 検定通過に向けた判定方針

本プロジェクトでは、以下の段階で適合性を判定する。

| 段階 | 判定対象 | 判定結果の意味 |
| --- | --- | --- |
| 設計レビュー | 仕様書、リール配列、役構成、抽選、停止制御 | 法令・解釈基準と明確に矛盾していないかを確認する |
| 数理レビュー | 出玉率、役物比率、短中長期分布 | 設計値とシミュレーション値が規格範囲内に収まるかを確認する |
| 実装レビュー | コアエンジン、乱数、状態遷移、ログ | 仕様書通りに動くかを確認する |
| 表示レビュー | 液晶、告知ランプ、筐体表示 | 出玉性能や遊技結果を誤認させないかを確認する |
| 実機化レビュー | 主制御基板、ROM、筐体、回路、電源、外部端子 | 型式試験に提出可能な物理構成かを確認する |
| 提出前レビュー | 申請書、諸元表、説明書、写真、取扱説明書 | 指定試験機関へ出せる資料一式になっているかを確認する |

## Aタイプ告知機としての予備チェック

| 項目 | 現時点の方針 | 予備判定 | 対応 |
| --- | --- | --- | --- |
| 機種タイプ | 液晶付き Aタイプ告知機 | 継続可 | AT/ART前提の文言を排除し、ボーナス主体に固定する |
| リール | 3リールを想定 | 未検証 | リール配列、図柄数、回転速度、停止制御を仕様化する |
| 図柄識別 | 筐体画像では装飾が強い | 要注意 | リール窓周辺の発光が図柄識別を妨げない設計にする |
| 告知 | ランプ/告知エリアで明確に伝える | 継続可 | 告知が内部抽せん回数や出玉性能を誤認させないよう仕様化する |
| 液晶 | 通常時/告知/ボーナス/エラー表示 | 要注意 | 回胴の停止結果を阻害せず、演出用図柄が結果表示を誤認させないよう制限する |
| BET | MAX BET/1BET 系を想定 | 未検証 | スマスロの遊技メダル数表示と投入操作を規則に合わせて定義する |
| STOP | STOP 3個を想定 | 継続可 | 各停止ボタンと各回胴の一対一対応を固定する |
| オートプレイ | デバッグ用に予定 | 実機では不可 | 実機仕様には入れず、エミュレーター専用機能として分離する |
| 設定変更 | デバッグUIに予定 | 実機では要分離 | 遊技者が操作できない構造、設定変更中の外部認識を仕様化する |
| 出玉性能 | 未設計 | 未検証 | 400回、1,600回、6,000回、17,500回、1時間、4時間、10時間等の検証を実装する |
| 役物比率 | 未設計 | 未検証 | BIG/REG の役物扱いと比率を仕様化し、シミュレーションで検証する |
| ROM | なし | 未達 | 主制御ROM、未使用領域、チェックサム、データ領域管理が必要 |

## 画像案を踏まえた検定リスク

### リスク 1: 装飾過多による図柄識別阻害

黒ベース案と金装飾案は、リール周辺の発光が強い。実機化する場合、回胴上の図柄を識別する部分について、光、反射、装飾、ガラス形状が識別を妨げない設計にする必要がある。

対応:

- リール窓周辺の発光を通常時は低輝度にする
- リール停止中も図柄が明確に見えるコントラストを確保する
- 告知時のフラッシュはリール窓に重ねない

### リスク 2: 液晶演出による誤認

液晶に大きな「BONUS」や演出図柄を表示する場合、内部抽せん、停止結果、ボーナス種別、出玉性能を誤認させるおそれがある。

対応:

- 液晶は補助演出とし、役判定はリール停止結果と仕様書で定義する
- 1回の遊技で複数回抽せんしたように見える演出を禁止する
- 出玉性能を期待させる数値やランキング表示を初期版では出さない

### リスク 3: デバッグ機能の混入

エミュレーターにはオートプレイ、設定変更、ログ出力が必要だが、実機仕様に混入すると検定上の問題になりうる。

対応:

- `debug` 機能はエミュレーター専用として明示する
- 実機仕様書ではデバッグUIを除外する
- コアエンジンでも「試験用機能」と「実機相当機能」を分離する

## 今後の必須検証

1. 別表第五チェックリストを完成させる
2. Aタイプ仕様のリール配列、役構成、抽選確率、払出を定義する
3. 400回、1,600回、6,000回、17,500回のシミュレーションを実装する
4. 1時間、4時間、10時間の試射相当シミュレーションを実装する
5. 役物比率、連続役物比率を算出する
6. 液晶/告知/音の誤認リスクチェックを作る
7. スマスロの遊技メダル数表示、投入、送信、精算に関する仕様を作る
8. 実機化時に必要な主制御ROM、基板、回路、筐体、写真、取扱説明書のテンプレートを作る

詳細なチェック項目は `docs/regulatory/compliance-checklist.md` で管理する。
